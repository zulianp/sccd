\section{Results}
\label{sec:results}

The evaluation answers three questions in order. Is the pipeline conservative?
How close does it come to the exact roots, beside a certified reference? What
does it cost on each processor? \Cref{sec:results:cons,sec:results:ref} settle
the first two together. The third occupies the rest of the section, including
the two places where the pipeline loses.

\subsection{Setup and dataset}
\label{sec:results:setup}

All measurements are taken on one \textsc{NVIDIA GH200} node of the CSCS Alps
system, with the Grace host and the Hopper (sm\_90) device in the same
allocation. The build uses \texttt{prgenv-gnu/24.11:v2} at \texttt{-O3} with
\texttt{CMAKE\_CUDA\_ARCHITECTURES=90}, at the default search parameters: a depth
cap of $69$ and a distance tolerance of $3\times10^{-8}$. Host loops are
scheduled with OpenMP~\citep{dagum1998openmp}. oneTBB~\citep{onetbb} is an
alternative backend and is not used here.

The timing protocol bounds what the numbers can support, so we state it. Each case is timed as three consecutive calls with their own clocks, reported as
two phases, which every table and figure names with the same four tags.
\emph{BP full} is the whole broad phase: building the swept boxes and the
acceleration structure, then querying it for overlaps. It decomposes into
\emph{BP prep}, the structure, and \emph{BP queries}, the overlap queries over
it, which are the two calls the harness times apart. The narrow phase is named
by the answer it is asked for, because the two cost differently: \emph{NP EToI}
returns one earliest time of impact for the step, so every query prunes against
the running minimum, while \emph{NP per-pair} returns one time of impact per
candidate and has no shared bound to prune with. Unless a table names per-pair,
its narrow-phase column is NP EToI. A figure or table that reports only part of
a phase says which part in its caption.

Device timings bracket every clock with a synchronisation, before it starts and
before it stops. A device phase ends with a kernel launch, which returns long
before the kernel finishes, so an unsynchronised clock charges a phase's tail to
whichever later call happens to wait -- BP full reads low and NP high by the
same amount. The competitor harness synchronises the same way, so the two
measure the same thing. The first case of a scene is run once untimed, to pay for
allocation and first touch. Repeats are separate processes, because the driver
measures each case once per run and run-to-run spread is visible only across
processes; three repeats are reported throughout. Every table gives the
\emph{median and the slowest repeat} as \texttt{median / max}. A median
describes the run one is likely to get and says nothing about the run one has to
budget for.

Two different variances matter, and the paper keeps them apart. \emph{Between}
job allocations this harness varies by about $40\%$. Everything compared against
anything else is therefore measured inside a single allocation, and no number
here is placed beside one from a different allocation. \emph{Within} an
allocation, the spread across the three repeats of a whole broad phase runs from
$0.3\%$ to $3.4\%$, depending on the scene and the strategy. That second figure,
and not the first, is the floor for claiming a difference. Margins close to it
are reported below as ties.

The measurements run on the time-of-impact dataset of
\citet{belgrod2025toi,nyuccd}. It holds six simulation scenes, three of them
drawn from the University of North Carolina Dynamic Scene
Benchmark~\citep{curtis2012unc}. Each frame is supplied both as a mesh pair and
as a curated query set whose coordinates are exact dyadic rationals and whose
roots were computed symbolically. \Cref{tab:dataset} gives the sizes. A
\emph{case} is one query type on one frame, so a simulation step is two cases.

\subsection{Conservativeness}
\label{sec:results:cons}

\Cref{tab:conservativeness} is the primary result. Every query carrying an exact
root is compared against it, signed, on both processors and all six scenes.
Summing the table, $5{,}815{,}032$ queries carry ground-truth data and are
checked on each of two processors. That gives $11{,}630{,}064$ query-mode
checks, of which $11{,}044{,}766$ place a reported time of impact beside an
exact root and do not merely agree that there is none. No collision is missed,
and no time of impact is reported after the true one.

\input{generated/tables/tab-conservativeness}

The comparison is against the dataset's exact roots and not against
TightInclusion, and that choice matters. TightInclusion's own answer is a
conservative lower bound on the truth. Scoring lateness against it would
therefore count as a violation every case where our search happens to land
closer to the root than the reference does.

False positives range from $1$ on cloth-ball to $1{,}245$ on rod-twist. By
\cref{thm:conservative} they cost work and never safety, and they are reported
here as the price of the guarantee, not as errors.

\subsection{Against TightInclusion}
\label{sec:results:ref}

TightInclusion is used exactly as released. Both sides are given the same task
on the same machine. SCCD reports one time of impact per pair, TightInclusion
runs unbounded over the whole step, and both are scheduled through the same
dynamic parallel loop. TightInclusion is run depth-first, which is its faster
configuration when there is no bound to exploit. It runs on the host, so in
\cref{tab:reference} the CPU row is the like-for-like comparison, and the GPU
row shows what the same search costs on the other processor.

\input{generated/tables/tab-reference}

On accuracy TightInclusion is a subject here and not the standard. Its answer is
a lower bound too, so the question is how close each implementation gets to the
exact roots. \Cref{tab:earliness-ref} reports \emph{earliness}, meaning how far
before the true root each implementation lands, as a median over cases and as
the worst case anywhere in the scene.

\input{generated/tables/tab-earliness-ref}

\Cref{tab:earliness-ref} is the paper's sharpest result and the empirical
counterpart of \cref{prop:order}. On the host, the median and the worst case
are \emph{identical to TightInclusion's on all twelve scene-phases, to every
printed digit}. We do not approximate the reference; we reproduce it, between
$1.6\times$ and $3.7\times$ faster.

The device agrees closely without agreeing exactly. The residue is small enough
to round away, and we state it instead. Its worst case is identical on eleven of
the twelve scene-phases. On the twelfth, armadillo-rollers vertex-face, it
reports $9.81\times10^{-3}$ against the reference's $9.39\times10^{-3}$. That is
$4.5\%$ \emph{further before} the root, and therefore on the safe side. Its
medians are identical on seven of the twelve and differ by at most $2.9\%$ on
the rest, in both directions: tighter than the reference on armadillo-rollers,
cloth-ball and puffer-ball, and looser on rod-twist.

The traversal order is not the cause. \Cref{prop:order} covers that, and this
comparison reports one time of impact per candidate pair, so no shared minimum
exists for threads to race over. The cause is that the device evaluates the same
mathematics through a different, equally valid sequence of floating-point
operations: vector fused multiply-adds for the corner values, and for $\delta^3$ in \cref{eq:err} a plain cube scaled to round upward. Both sequences stay within the certified bound, so both are
conservative. A box whose classification is decided in the last few units in the
last place can nevertheless fall either way. That is why the device comes out tighter than the reference on some rows and looser
on others. Where the device additionally discards work under queue
pressure (\cref{sec:parallel:device}), the effect is one-sided and safe. Every
value in \cref{tab:earliness-ref} is at or before the exact root.

The worst cases belong to the problem and not to the implementation. On
cloth-funnel and rod-twist the largest error approaches $1.0$ for the reference
as well. A conservative search has no tighter answer available on a grazing or
already-touching configuration, because the root box cannot be refined away when
the contact is at the very start of the step.

\subsection{CPU against GPU}
\label{sec:results:proc}

\input{generated/tables/tab-processor}

\Cref{tab:processor} puts the two processors side by side as whole-scene totals,
and the split follows \cref{sec:parallel:why} mechanically. The broad phase is
count, prefix sum and scatter, with no sequential window walk, and it runs at
$0.56\times$ to $2.90\times$ of host speed: a modest range, ahead on the three
largest scenes and behind on the three smallest. The narrow phase is a divergent
depth-first search, and it spans a far wider range, $0.41\times$ to
$15.14\times$: behind the host where the candidate lists are smallest, and ahead
by an order of magnitude on n-body and puffer-ball, where tens of millions of
candidates keep every lane busy. The device's advantage is therefore the narrow
phase, and the broad phase is what limits it.

End to end the two effects cancel to different degrees. The device wins
puffer-ball by $3.51\times$, n-body by $2.34\times$, rod-twist by $2.00\times$
and cloth-ball by $1.90\times$; the host wins armadillo-rollers at $0.70\times$
and cloth-funnel at $0.53\times$, where a device broad phase behind at
$0.56\times$ and a narrow phase behind at $0.41\times$ both point the same way.
Cloth-funnel is the smallest scene in the benchmark by candidate pairs and
puffer-ball the largest, and the device wins the larger one, so problem size is
not a rule for choosing a processor on its own. \Cref{sec:results:scaling} shows
what does move with it.

\Cref{tab:throughput} states the same comparison as a rate. Candidate pairs
resolved per second is the throughput figure for this pipeline. It is what the broad phase produces and the narrow phase consumes; it is
comparable between scenes that differ by three orders of magnitude in size; and
it rewards an implementation for resolving the same pairs with less work, which
is the direction this pipeline is designed to move in.

\subsection{The two broad-phase strategies}
\label{sec:results:bp}

\input{generated/tables/tab-broadphase}

\begin{figure}[htbp]
  \centering
  \input{tikz/broadphase}
  \caption{Why the two broad phases differ. Sorting on one axis prunes on one
    axis, which a draped surface defeats; the cell list bins instead and resolves
    the resulting duplicates by attributing each pair to the cell holding the
    minimum corner of the overlap.}
  \label{fig:bp}
\end{figure}

\Cref{fig:bp} contrasts the two algorithms on the geometry that separates them,
and \cref{tab:broadphase} measures them over the whole benchmark.

\textbf{The cell list wins or ties on every scene of the host, and the device
splits.} On the host it leads puffer-ball by $5.75\times$, armadillo-rollers by
$1.66\times$, cloth-funnel by $1.50\times$ and n-body by $1.10\times$, with
cloth-ball and rod-twist coming out ties, their margins inside the repeat spread
of \cref{sec:results:setup}. On the device the verdict is scene by scene: the
cell list leads puffer-ball by $2.81\times$ and rod-twist by $1.10\times$, the
sweep leads cloth-funnel by $1.77\times$ and armadillo-rollers by $1.13\times$,
and cloth-ball and n-body are ties. The largest margin is the largest scene:
$78.0\,\mathrm{s}$ against $448.8\,\mathrm{s}$ on the host over puffer-ball's
$240$ cases, and $26.8$ against $75.3$ on the device.

Summed over the whole benchmark the host choice is not close and the device
choice is carried by one scene. The cell list costs $138.7\,\mathrm{s}$ against
the sweep's $513.2$ on the host, a factor of $3.70$; on the device it costs
$62.5\,\mathrm{s}$ against $111.0$, a factor of $1.78$ of which puffer-ball
alone supplies $48.5\,\mathrm{s}$. Take puffer-ball out and the device totals
are $35.7\,\mathrm{s}$ against $35.7$: the same to three figures. What
\cref{sec:bp:cell} predicts -- that binning suits a device better than sorting,
being the count, prefix sum and scatter the rest of the pipeline is already
built from -- shows only where the scene is large enough to pay for the grid.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{figures/broad-per-frame.pdf}
  \caption{BP full through each simulation -- the acceleration structure and
    the queries over it added -- in milliseconds for one step, both query types
    together, against frame index. Colour carries the processor and
    intensity the strategy, the cell list at full strength and the sweep
    lightened. Both processors run both strategies over the same cases.}
  \label{fig:bpframe}
\end{figure}

\Cref{fig:bpframe} draws the same comparison step by step, and it shows the
margin to be a property of the scene rather than of a few frames. On puffer-ball
the sweep is the slower strategy on all $120$ of them. The two ties are ties for
different reasons: on cloth-ball the strategies trade frames, the sweep leading
on $24$ of $43$ and leading on the expensive ones, so the totals come out level;
on rod-twist the cell list leads on $1{,}821$ of $2{,}556$ frames and still ends
only $8\%$ ahead, because the frames it loses cost more than the frames it wins.

The device figure says something the totals do not. There the sweep leads most
frames of four scenes -- $225$ of armadillo's $396$, $26$ of cloth-ball's $43$,
$253$ of cloth-funnel's $372$ and $40$ of n-body's $74$ -- and still the cell
list takes the benchmark, because it does not lead a single frame of
puffer-ball, where one scene's margin outweighs the rest put together. Counting
frames and summing milliseconds disagree on the device, and the disagreement is
the result: a strategy chosen per frame and a strategy chosen per benchmark are
not the same choice.

The BP prep columns say where the difference comes from, and it is not where BP
queries alone would suggest. The sweep builds its sorted intervals at two to
four times the cost of the grid on the host, $29.1\,\mathrm{s}$ against $12.1$
on rod-twist and $10.1$ against $2.9$ on puffer-ball, because a sort is
$O(n\log n)$ where binning is linear, and the device keeps that ratio at
$14.1\,\mathrm{s}$ against $3.9$ and $11.5$ against $3.3$. What differs between
the processors is BP queries: on the host the grid's queries are cheaper too on
five scenes, while on the device the sorted intervals are queried faster on four
of the six, enough to overturn the structure's advantage everywhere except
puffer-ball and rod-twist.

\textbf{A fixed choice is defensible on this evidence, and we still do not make
one.} Nothing here would be lost by always running the cell list. What the race
protects against is the scene nobody measured: the two algorithms emit identical
pairs (\cref{prop:agree}), so the cost of being wrong about which is faster is
bounded by the ratio between them, and \cref{tab:broadphase} shows that ratio reaching $5.75\times$ within one
benchmark. Two probe steps out of a simulation
buy insurance against that at a cost we can measure and a reader can check. We
report the six scenes as the weak evidence for a fixed choice that they are, and
\cref{sec:bp:choose} reports the five predictors that failed to make the choice
without measuring.

\subsection{Against other implementations}
\label{sec:results:others}

\Cref{sec:results:ref} compares SCCD with the reference whose mathematics it
inherits. Two other implementations answer neighbouring questions, and each is
compared on the question it answers rather than on a single shared table. Both
are used exactly as released, built with the same compiler flags, and run on the
same node over all six scenes and all $6{,}394$ cases, three repeats each.

\textbf{Scalable CCD} returns one earliest time of impact for a simulation step,
pruning every box against the running bound~\citep{belgrod2025toi}. Both
libraries therefore run their earliest-time-of-impact path once per case from a
bound of $1$, over identical broad-phase candidates, and \cref{tab:competitor-earliest}
scores the step's answer against the step's earliest exact root.

\input{generated/tables/tab-competitor-earliest}

End to end SCCD on the device is ahead on every scene, from $3.0\times$ on
cloth-funnel to $10.3\times$ on puffer-ball, and the whole-scene totals put the
cost in the terms a simulation pays: $34.9$ against $143.6\,\mathrm{s}$ over
rod-twist's $4{,}571$ cases, $27.1$ against $278.3\,\mathrm{s}$ over
puffer-ball's $240$. Puffer-ball is also where our host path loses outright, at
$461.1\,\mathrm{s}$, because its broad phase carries the scene on its own. The
comparison is on the device throughout: Scalable CCD's narrow phase is CUDA, so
its host side is a broad phase with no pipeline behind it and not something a
caller runs end to end.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{figures/broad-vs-scalable.pdf}
  \caption{Device BP full against Scalable CCD's, step by step -- the
    acceleration structure and the queries over it added -- in milliseconds for
    one step, both query types together. All three curves come from one
    comparison run, so they are measured in one allocation. Both of our
    strategies are drawn, because which of the two is running accounts for part
    of the difference.}
  \label{fig:bpvs}
\end{figure}

\Cref{fig:bpvs} puts the broad phases side by side through each simulation.
Summed over the benchmark ours costs $30.3\,\mathrm{s}$ against
$313.8\,\mathrm{s}$, and the margin is a standing one rather than a few
expensive steps: on puffer-ball, the scene with the most candidate pairs, it is
$10.4\,\mathrm{s}$ against $227.2$. Drawing both of our strategies separates
what the implementation earns from what the choice of algorithm earns, and on
n-body the two answers differ: our sweep is the slower broad phase there,
$7.4\,\mathrm{s}$ against Scalable CCD's $6.3$, while our cell list takes the
scene at $1.9$. On cloth-funnel the ordering is the other way round -- our two
strategies are within $4\%$ of each other, so the $5.0\times$ against Scalable
CCD is the implementation and not the algorithm.

The earliness columns are the ones to read carefully, because on three scenes
they report a defect rather than a difference in tightness. On armadillo-rollers
Scalable CCD's answer lands after the true root on $272$ of the $394$ steps that
carry a contact -- its median earliness is $-9.8\times10^{-3}$, so the median
step is late, and its own \emph{tighter} entry reads \emph{late} because a ratio
against a late answer would not measure tightness -- and its worst answer misses by
$1.000$, reporting no contact at all where one exists early. It is late on $36$
of rod-twist's $2{,}481$ steps and $10$ of cloth-funnel's $363$, and on none of
cloth-ball's, n-body's or puffer-ball's. Where it does stay conservative it is
still the looser answer, by $55\times$ on cloth-ball, $279\times$ on rod-twist
and $3{,}060\times$ on puffer-ball.
The cause is a race in its subdivision buffer, whose overflow check tests that
the buffer is full and then advances the tail as two separate operations, so
that concurrent pushes can wrap the tail onto domains that have not been
processed yet with no overflow flagged. Three observations identify it. Padding a
query list with pairs that fail their first inclusion test -- which changes
nothing but the length of the list, and hence the size the buffer is given --
turns $0$ of $1{,}299$ contacts found at one step into all $1{,}299$. The answer
differs between identical runs. And a copy of the library whose overflow check is
made race-free finds every one of the $54{,}664$ curated contacts of armadillo's
first $400$ cases with nothing missed and nothing late. The comparison above
reports the library as published; the patched copy is diagnosis only.

Which scenes it bites is itself evidence for that reading. The buffer is sized
from the number of queries it is handed, so a short candidate list gives a small
buffer: the three scenes it fails are the three with the fewest candidate pairs
per step in \cref{tab:dataset}, and the three it answers correctly are those
with millions.

\textbf{Additive CCD} answers per pair, advancing conservatively until contact
rather than isolating a root~\citep{li2021codim}. It is the narrow phase of a
different trade, and \cref{tab:competitor-pair} puts the two on the same
candidates and the same curated queries.

\input{generated/tables/tab-competitor-pair}

It is the cheaper narrow phase on every scene, by $2.1\times$ per candidate on
cloth-funnel, $5.0\times$ to $5.3\times$ on armadillo-rollers, cloth-ball, n-body
and puffer-ball, and $12.1\times$ on rod-twist, against \textsc{Tight} on the
host: $6.8$ against $82.3\,\mathrm{s}$ over the whole of rod-twist.

What it buys with that is the answer. Its median earliness runs from
$8.6\times10^{-3}$ to $1.1\times10^{-1}$ where \textsc{Tight}'s runs from
$3.0\times10^{-8}$ to $2.8\times10^{-4}$, which the \emph{tighter} column puts at
$85\times$ further from the root on rod-twist, $2{,}600\times$ on puffer-ball and
$2.1$ million$\times$ on n-body. Its worst case gives up almost the entire
step on every scene, between $0.897$ and $0.996$. The same gap shows in the false
positives, $444$ against $24$ on armadillo-rollers and $27{,}374$ against $536$ on
puffer-ball. That last figure is worth putting beside \cref{sec:results:relaxed}:
on the same scene our own \textsc{Relaxed} reports $27{,}380$, so additive CCD at
its shipped $0.9$ rescaling sits about where the looser of our two acceptance
tests does. Neither library misses a contact anywhere, and every earliness in
\cref{tab:competitor-pair} is positive, so neither answers after a root -- which
is what \cref{thm:conservative} and the method's own construction each guarantee.
A solver pays for the gap with a shortened step.

\subsection{Scaling with element count}
\label{sec:results:scaling}

\Cref{tab:scaling} refines one surface repeatedly, quadrupling the element count
at each level from $92{,}230$ to $23.6$ million, over cloth-ball frames $0$ and
$1$. Those two frames do not come into contact, which is what makes the broad
phase the quantity the study measures.

\textbf{The host cell list leads the device broad phase at every size measured,
and the gap widens.} \Cref{fig:scaling} plots both phases against the element
count on logarithmic axes. Dividing the \emph{broad} column of \cref{tab:scaling}, the host is $1.65\times$
ahead at $92{,}230$ elements ($4.0\,\mathrm{ms}$ against $6.6$), $1.94\times$ at
$1.48$ million ($67.9$ against $131.4$), $4.89\times$ at $23.6$ million
($998.7$ against $4883.7$) and $7.71\times$ at $94.4$ million ($4791.5$ against
$36922.5$). The fitted exponents say why: the device broad phase
grows at $1.21$ in the element count against the host cell list's $1.00$.

The structure columns locate the difference. At $23.6$ million elements the host
builds its grid in $233.3\,\mathrm{ms}$ where the device builds its sorted
intervals in $2123.3$, a factor of $9.1$, and that one column is over two fifths
of the device's whole broad phase. The device sorts because its broad phase implements only the
sweep (\cref{sec:limitations}); the cell list exists as a device kernel and is
not wired into the device mesh path, so this comparison is between two algorithms
as much as between two processors.

The host sweep is the control that separates those two explanations. Run on the
same frames it reaches $11470.7\,\mathrm{ms}$ at $23.6$ million elements
against the cell list's $998.7$, a factor of $11.5$, and its traversal alone is
$11052.0\,\mathrm{ms}$. The algorithm, and not the processor, is what costs most
here.

The narrow-phase columns of \cref{tab:scaling} measure something different and
should be read with care. These two frames do not come into contact, so no root
is ever isolated and the column prices the rejection test alone, over candidates
that all fail it. That work is uniform, which is the shape a GPU handles best:
across the six refinements the device stays between $1.6$ and
$13.8\,\mathrm{ms}$ while the host climbs from $0.4$ to $118.2$, so the device
ends $8.6\times$ ahead on the column where it was furthest behind at the coarsest
size. It says nothing about the divergent case, where the search actually
descends. \Cref{fig:percase} gives narrow-phase cost against genuine problem
size, over cases that do collide.

\subsection{Scaling with thread count}
\label{sec:results:threads}

\Cref{sec:results:scaling} varies the problem and holds the machine fixed.
\Cref{fig:strong} does the opposite, running the same four cases at one to
seventy-two Grace cores.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{figures/strong-scaling.pdf}
  \caption{Strong scaling of the host pipeline, by phase, as whole-scene totals
    against the perfect line. The narrow phase tracks it closely; the structure
    the broad phase builds leaves it early and plateaus around thirty-two
    cores.}
  \label{fig:strong}
\end{figure}

The narrow phase scales close to perfectly, reaching $56\times$ on cloth-funnel
and $35\times$ on armadillo-rollers at seventy-two cores. That is what
\cref{alg:host} is built for: lanes are filled from a per-block stack, blocks are
independent, and the only shared state is an atomic minimum, written rarely. The
broad phase's traversal reaches $23\times$ and $30\times$.

\textbf{Building the acceleration structure is what stops scaling.} It reaches
$3.5\times$ on cloth-funnel and $5.5\times$ on armadillo-rollers at
thirty-two cores and improves no further, where the two phases beside it are at
$11$ and $17$. The consequence is the familiar one: a component that takes $5$ to
$7\%$ of the single-core time takes $34$ to $40\%$ of it at seventy-two, and it
holds the whole pipeline to about $21\times$.

Three passes over every box account for the plateau, and all three are
reductions or histograms whose parallel forms are ordinary: the centre-variance
reduction that picks the sort axis, the extent and mean reduction that sizes the
grid of \cref{sec:bp:cell}, and the counting histogram that fills it. Making
them parallel is what took this curve from the $2.4\times$ an earlier version of
this code reached to the figures above, and it left the traversal and the narrow
phase untouched. What remains is a floor. At seventy-two cores the structure pass costs a few
milliseconds per case whether the case carries $27{,}918$ candidate pairs or
$388{,}206$, so the residue is a fixed cost per call.

Both scenes are slower at seventy-two cores than at sixty-four, in every phase.
That belongs to the node and not to any one phase, and it is why the figures
above are quoted at the plateau.

\subsection{Trading accuracy for speed}
\label{sec:results:relaxed}

\textsc{Relaxed} accepts a box sooner (\cref{sec:np:modes}). Against
\textsc{Tight} on the same cases it is looser at the median earliness by
$27\times$ on armadillo-rollers, $9.21\times10^{-5}$ against
$3.41\times10^{-6}$, and it produces far more false positives. It is as conservative as \textsc{Tight}, with zero missed
and zero late, because by \cref{thm:conservative} a looser acceptance test
reports earlier and never later. The false-positive cost is not a rounding
error, however. On rod-twist it reports $244{,}973$ contacts that do not exist against
\textsc{Tight}'s $1{,}245$, on $285{,}431$ queries carrying an exact root, which
is better than four in five of the queries it answers. On puffer-ball the figure
is $27{,}380$ against $558$. A solver pays for each of those with a shortened
step, so on those two scenes \textsc{Relaxed} buys nothing: it is slower on the
host and far less useful. It earns its place on the device, and on scenes whose
contact set is small.

The speed it buys is uneven. Accepting a box sooner also hands the next query a
looser shared bound, so the search prunes less, and on the host that can cost
more than the earlier acceptance saves. The accuracy cost is unconditional; the speed gain is not.
That asymmetry is why each mode gets its own table, and why both appear here.
